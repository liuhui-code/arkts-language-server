# checkpoint-23递增文件规模复核

核对日期：2026-10-20。结论：**最新版本有同条件递增规模数据；全局rename和编辑后
首次references仍随实际Program输入明显增长。23降低了多档耗时，尚无规模增长成本
已下降的证据。** 成员补全/定义因语义组范围固定，增长较小，不能推广到有效依赖
本身增长的项目。本次只分析已有封存记录，没有修改产品代码或新增性能运行。

这是端点差值，不是回归斜率或每文件成本。结论分开如下：

1. **收益不只固定规模。** 23各档首次references中位数均下降：合成约30–44ms，
   Photos约37–56ms；1024档三次都进入500ms以内，扩大规模仍有绝对收益。
2. **没有显示规模增长成本整体下降。** 合成rename和首次references端点增量
   均未降低；Photos增量略降但没有跨cohort一致改善。23更接近移除共享固定开销，
   没有证据支持复杂度阶数改变，也不能用更低基线下更高相对百分比断言算法退化。
3. **仍明显增长的是全局查询。** 23合成64→2048时rename约+69%、首次references
   约+78%；Photos完整Program284→796时分别约+51%和+41%，均在各中间档同向增长。
   2048的三次rename和三次首次references，以及Photos+512三次首次references仍FAIL500。
4. **交互组固定时，成员查询增长较小。** 合成首次补全约+11ms/3.3%，且中间档
   不单调；热定义约+7.5ms，重复补全约+8.6ms。首次重开定义47.6→65.9ms有正向
   增长，Photos对应219.2→238.8ms；Photos重复补全/磁盘热定义没有明显单调趋势。
   不能把“Program文件数固定”写成“查询与项目文件数完全无关”。
5. **结果缓存命中没有一致增长趋势。** 各档约1.5–1.9ms中位数，最大2.258ms；
   这是相同输入下结果命中，不是编辑后或输入变化后的完整语义查询性能。

## 调用链依据与可测边界

- [LegacySemanticEngine.rename](../../src/semantic/legacy-semantic-engine.ts)显式
  `prepare(..., true)`，纳入完整项目。实际trace确认其Program数与首次references
  的完整范围一致；成员查询由稳定组选择，范围分别固定19/171。
- [DocumentStore.collectDependencyClosure/reuseDependencyClosure](../../src/core/workspace/document-store.ts)
  检查root内容代次；正文编辑后即使import不变，也可能重新解析依赖图。
  实际发现次数同cohort一直18/137，不随新增noise变多，不能把文件增长都归于依赖扇出。
- [TypeScriptResidentReferenceState](../../src/core/types/typescript-resident-reference-state.ts)
  的`observe`/`covers`/`diskInputsCurrent`处理实际Sources，`inputsFor/normalizedPaths`
  处理成员/根并排序，输入越多，需处理的项越多；终检仍独立重新验证。
- [Host getScriptSnapshot](../../src/core/types/typescript-language-service.ts)及
  [TypeScriptLazySnapshots](../../src/core/types/typescript-lazy-snapshots.ts)仍同步项目
  输入。2048 trace在仅1个项目解析入口、SDK0的同时，仍读取1664份未变项目文本；
  SourceFile对象复用并不等于零Host读取或零Program同步。
- [SemanticGroups.all](../../src/core/types/semantic-groups.ts)仍比较完整membership列表，
  所以小Program不代表完全不接触项目成员元数据。其正常独占时间未测，不能将
  本轮成员操作多出的几毫秒精确归到此函数。
- [CompilerSourceReadFacts](../../src/core/types/compiler-source-snapshots.ts)复用已验证
  compiler snapshot；23在所有7档首次references trace中SDK文本读305/255→0，
  其他库52→0。SDK/库规模同cohort不变，当前和独立终检仍保留；该机制支持减少
  共同开销的解释，未取消随项目Program成员增长的同步和核验工作。

以上正常RPC内部独占占比未测。重探针下2048 compiler约1389.9ms，而正常RPC约
612ms，不能直接分摊；import扫描的异常长停顿及GC原因未测，不能指定归因。
该引用路径未出现逐批verifier/candidate选择事件，不把当前增长归为64/1024根批次。

代码可支持个别遍历随Sources增多、排序随成员数增多，但**本次不将整体RPC定为
O(N)、O(NlogN)或O(N²)**。只有4个合成档/3个Photos档、每档3次；两cohort的SDK
和代码量不同，分开分析。最大同条件多轮规模为2048，几万文件未测；8250功能/
带探针单点不纳入本轮曲线。23没有在本轮重做“有效依赖组本身增大”、扇出/深度、
单文件体量和引用数量的矩阵，固定组成员查询的结论不能扩展到这些变量。
