## 已证根因与现场边界

用户报告真实三万文件工程必现反复重建至不可用，但没有该现场日志。
不能从索引 99% 推定是普通语义请求 30s 截止；索引和语义初始化独立。

真实 server 子进程公开回归证明：正常启动输入或客户端取消遇到已经开始的 Program 同步时，
原 watchdog 将一段有限、无检查点的同步按 1000ms 取消静默判为 Worker 故障。
原 Worker 被退休，后继定义可能返回 -32603；反复发生会进入既有恢复预算和熔断路径。
Worker 内早已按 TypeScript 一致性要求暂缓协作取消，但父端的物理终止没有遵守同一边界。

控制实验在真实编译器调用内插入 1800ms 有限等待，未伪造协议或修改 watchdog。
它证明父端判定可错误退休有限工作，不证明用户现场具体 CPU 热点或完全相同的时间窗口。

## 修复

仅修改现有 watchdog：匹配 epoch/id 且实际处于 synchronize/program/checker 时，
普通读取取消或输入失效立即撤销旧结果，同时允许该同步清算。
同步离开后恢复原 1000ms 终态交付宽限，后续更新不能重新授予已完成的清算。
已取消结果不会作为成功发布，也不会补充恢复预算；后继输入继续按现有版本/队列顺序应用。

从原开始点计算的绝对截止保持普通请求 30s、完整查询 120s、准备 180s。
永久同步、损坏取消 cell、真实构建/清算失败、关闭和最大三次自动恢复的保护继续生效。
不调整产品截止数值、V8、默认 RSS 策略、完整项目范围或缓存容量。

本方案沿用固定 TypeScript 4.9 的同步一致性边界和 clangd 的更新/取消读取分离思路，
不引入额外 compiler Worker、另一套恢复器或旧答案回退。官方来源及 Context7 限制记录于 ADR0031。
