## 内存口径及结果

主指标为 **唯一 PID 的进程树 RSS 之和**，标称每 250ms 一次，保留采样开始/结束
时间和前后 phase。跨 phase 的样本不算某个操作的期间峰值。根 Node 进程包含
LS 主线程及所有 Worker 线程；原生索引为独立子进程。没有把各线程报告的
process-wide RSS 再相加。RSS 之和仍可能重复统计进程间共享页，不是 PSS 或独占物理内存。
测量脚本、ps/sysctl 子进程不在语言服务器进程树内，不计入产品指标。

内存诊断另记录主 isolate 每 10ms 及 wire 边界的 RSS、各 isolate 每 250ms 的堆。
Worker 分线程 RSS 无法归属，明确未测；其堆观测和根 RSS 是不同口径，不能相加。

## 增长原因的证据与限制

文件数 9.77 倍，正常时延中位数：初始准备 2.71 倍、重命名 12.24 倍、首次编辑
引用 13.10 倍；首次磁盘补全 2.12 倍、磁盘定义 3.95 倍。结果缓存命中基本不变。
普通树峰值中位数 1.36 倍；内存诊断全程 1.45 倍，最后空闲约 1.46 倍。
输入仅 0.50MB 且大部分是很小的无关源码，SDK/依赖/引用/复杂度固定；不能用该
内存增长比例外推真实多模块、深依赖或大文件 2 万源码项目。

代码及实际调用证据：

- `semantic-worker-host.ts:170` 使用 Worker 线程，解释为何共享根 PID 的 RSS
  只计一次；`typescript-semantic-readiness.ts:150` 附近取得实际 Program 并准备
  初始输入，即使随后因缺失 SDK import degraded。独立 observer 确认大组与完整组。
- `DocumentStore.collectDependencyClosure` / `reuseDependencyClosure`
  （`document-store.ts:1371/1474`）、`runOwnerReferenceQuery`
  （`reference-anchor-preparation.ts:37`）、`queryRetainedReferenceContext`
  （`resident-context-lease.ts:40`）及完整搜索范围检查位于请求路径。
- `TypeScriptLanguageServiceEngine` 调用官方 `service.getProgram()`、重命名和引用
  API；trace 明确记录 20000 个项目输入和各一次 createProgram。引用结果缓存
  命中则复用已有完整结果，不能代表失效后的成本。
- 独立内存诊断三轮：重命名 compiler 阶段中位数 2048 为 820.50ms、20000 为
  5649.36ms，其中 createProgram 中位数分别 552.69 / 5342.38ms。
  首次引用 compiler 阶段 231.03 / 2540.61ms，其中 createProgram
  147.43 / 1248.99ms。原始事件及完整阶段字段另存。
  这些是带 trace、堆观察及空闲停顿的诊断运行，不能分摊正常 7756ms 的占比；
  createProgram 是内层时间，也不能与 compiler 相加。

实测表明完整 Program 同步/官方查询路径的成本随本夹具规模明显放大；即使补全
Program 固定 19 项目文件，其 RPC 仍增长，因此缩小交互 Program 并未隔离全部
工作区规模成本。各扫描/身份核验/GC 对普通 RPC 的独占贡献、真实解析次数、
SDK 独占 AST 内存、PSS、线程 RSS 分摊及长期驻留泄漏均 **未测**，不推测归因。
这里只比较两个文件数端点，不能据中位数比值宣称 O(N)、O(N²) 或其他复杂度。
