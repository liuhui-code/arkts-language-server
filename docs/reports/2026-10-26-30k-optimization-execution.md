### 为什么缓存没有挡住本次

- 缓存只能复用已经建立、与当前输入匹配的状态。原 30K 初始化在 Program 构建前就因成员清单不完整返回；首次 definition 是这份上下文第一次真正构建 Program，不是复用一个完整热 Program。
- 初始化预装了项目文本，驻留文本又被当作根入口。109 个 CommonComponents barrel 对应多份复制后的真实 export/import 关系；它们扩大了实际输入集合，AST 共享并不自动删掉这些错误入口。
- 旧官方模块解析缓存仅覆盖 fallback 路径，且有 32 次限制；本次大热点走相对候选/Harmony/路径身份核验，不能因“有模块缓存”就认为全部命中。
- 身份元数据共享优化用于请求内当前/终检阶段；`LoadedConfigurationWitness.observe` 的实际加载前后证明原来仍逐次执行。首查正确性核验和结果缓存不是同一层。
- 引用结果缓存要求同输入资格。编辑后的首次查询本来就不等于相同结果缓存命中；本次没有把低时延自动标为命中。

## 2. 用用户操作解释这些状态

**初始化**先识别项目/SDK、枚举源码清单、准备 SDK 和允许的语义上下文。
“初始化流程结束”和“全项目语义已完整就绪”是两件事；失败或输入不完整也必须结束流程、返回明确状态。

**后台诊断**是服务器在 didOpen/didChange 后 75ms 去抖启动的检查，给编辑器红线；用户不必点它。
**用户查询**是 definition、completion、references 等请求，和后台诊断共享语义执行资源，所以可能排队。

**Program**是 TypeScript 编译器的一份语义视图：根文件、它们真正引用的依赖和类型检查状态。
它不是操作系统进程，也不是“每 64 个文件一个批次”。本次 definition/diagnose 走常驻 LS/Program，
没有进入引用 verifier 的分批路径。所谓“交互 Program”，只是被当前局部编辑/导航所使用的那份视图。

30K 源码枚举超过默认 20000 条路径保护上限，`membership.status=partial`：**文件清单不完整，
不是某个源码只解析了一半**。该保护同时有 4MiB 路径字符串边界，避免无约束目录/元数据增长。
公开 readiness 因而是 `degraded / project-membership-incomplete`；局部已知符号仍可查询，不能把前 20000 文件当成完整工程返回全项目引用/重命名。
它与 SDK 缺某个声明导致的 SDK partial 是不同层，不能把局部未知升级成整个服务进程失败。

原真实 Zed 的线程来历：04:42:58.993 创建第一条语义 Worker（thread 1），运行的是已核验的 main 新包。
04:43:04.315 客户端发 didClose，紧接 didOpen 同文件/v0/相同文本；捕获记录没有 UI 内部事件来源，不能编造为用户主动关闭。
服务器因此撤销旧文档诊断的新鲜度，正在运行的 diagnose 被 mutation 标为 content-modified。
它在同步构建中不能安全任意退出，原父端仍在约 1s 后退役它；新的高亮/codeAction 已在该线程所属队列等待，随队列被销毁。
04:43:06.734 才创建替代 Worker（thread 2）。因此“旧”仅指这次会话中首先创建、随后被替换的线程，**不是运行了旧安装包**。

语言服务器父进程保留最新 roots、配置、SDK 选择、未保存文档文本/版本；恢复时向替代线程回放。
Program、checker、AST、线程内缓存不跨 isolate 迁移；退出才解除原线程的资源责任，进程 RSS 不保证立刻下降。
原错误发生在 thread 2 启动前；recovery.complete 只证明输入回放，不证明新 Program 已准备或 READY。
原 UI 没有替代线程上的真实点击重试，本次协议验证与真实 UI 始终分开。

运行指标`projectFiles=60000`也不是60000个项目文件或AST：它累计各驻留上下文持有的成员元数据，
实际文件数要看这里的`sourceFileList`。不拿它证明重复AST分配或泄漏。

合成夹具位于仓库的隔离目录，除固定SDK256与标准库52外，实际还自动载入祖先`node_modules/@types/node`的61份声明；
这61份在同轴各档/两版中保持不变。真实外部30K不继承它们，因此其他文件52，不能把合成与真实项目当成同一共享依赖条件。
直接项目闭包18与实际Program总数387是不同口径。原Photos288测试副本也在仓库内；它与外部30K不是纯N单变量。

### 8.3 realpath的完整分布与边界

原186768次来自旧诊断窗口，该探针只保留前4096路径频次，无法事后精确还原全部唯一数，原限制未删除。
新独立旧main完整分布的最终检查点（解析7200份，Program仍未返回）为：

- 总native realpath 180818次、7515个唯一路径；Program中176895次。
- 项目162911 / SDK12121 / 其他5786；调用点witness138258 / installed-source34264 / 其他8296。
- 单路径最高16367次，是`common/src/main/ets/default/utils`；另一个`model/common`目录16086次。
- 唯一路径按调用频次分桶：1次29个、2–9次5292个、10–99次2030个、100–999次153个、1000次以上11个。

因此18万不是18万个不同文件；缺失候选不断回溯同一父目录，加载前/后证明再次realpath，
导入者物理来源仍需核验。大入口图使这些按边/候选发生的工作相乘。
首次资格检查是正确性需要，**同次同步查询重复选择同一base候选**可以复用；S2的60个SDK导入用例证明61→1，
后建高优先级候选、符号链接/身份边界及读取窗口仍通过拒绝旧资格回归。
新候选先有实际load witness，1MiB估算预算内复用；溢出普通解析，同步结束清空，未把负结果永久保存。

新真实30K local createProgram为3391次realpath，首个语义定义命令连准备/终检5318次；热定义634次，
SDK初始化8448次。SDK-only Program到局部Program累计9734次，不能全算给首次查询。
主要下降来自移除错误入口，S2的单独收益由受控重复候选测试证明，不能把全部18万下降归给候选缓存。
计数是观察器拦截的Node同步FS API调用，不等于全部OS系统调用；“其他”未完全归因。

## 9. 结论、边界与后续优先级

1. **修复了错误工作量，不是证明所有功能恒定耗时。** 原30K的281项目入口包含109个barrel，
   初始化脚本残留跨到交互根，实际编译器沿这些合法export/import扩大图；本次初始化项目根0，局部根/实际项目文件87。
   这不是因为每次点击必须扫描全部30000源码，也没有证明原编译器死循环。
2. **完整清单下仍有N成本。** 固定闭包、64→2048→19999→20000时，v5热定义中位数约29.5→36.9→165.1→166.8ms；
   编辑首引用在约241ms→数百ms→约4.4s。`SemanticGroups.all`的membership.paths.every、
   全范围资格/身份核验和global Program路径仍有按N遍历。Program复用不等于这些步骤被跳过。
   当前合同下的全范围校验有其原因，但这不是理论上无法优化；root引用缓存/版本/证明重做的原TODO仍未在此扩展实现。
3. **跨20K不是同一算法的平滑曲线。** partial跳过完整组与全根准备，SDK仍提前解析；
   局部热态20001/30000同闭包的Program输入和文件访问基本固定，但完整引用/rename被明确拒绝。
   不能以30000比20000更快或RSS更低证明大型项目全功能已解决。
4. **真实闭包成本仍在。** 总数固定30000，项目闭包18→258→2050时，解析/校验/模块解析输入增长，
   局部首查、编辑、重开均明显变慢。实际输入首次解析和输出结果存在输入/输出规模成本；
   本实验同时改变Graph导入数与表达文本规模，没有单独分离这些因素，不能只凭相关性断言整条请求O(N)、O(NlogN)或O(N²)。
