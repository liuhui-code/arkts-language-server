477 次包含 471 个 RPC 响应和 6 个诊断通知；同时满足所选功能检查与 ≤500ms 的为 181 次。补全检查验证预期目标存在，未使用穷举补全集合 oracle。定义、isVisibility 的四处引用、最新编辑后的行号、诊断版本和修复结果有显式预期。普通补全返回 `isIncomplete=true`，该标志保留在原始数据中。

输入测试将 `this.isVisibility` 改成 `this.isV` 后立即补全，并通过增量头部插入验证定义行号更新。自动导入已返回 MenuContext 和一处额外导入编辑；重命名预览已返回预期四处编辑。这两类返回编辑的实际应用、应用后的跨模块跳转和重命名引用复核，属于断连后尚未执行的额外验证。

三轮初始化通知分别在 **14552.2 / 14511.2 / 14470.3ms** 到达，状态全部为 **degraded**。此前首次探测为 31944.4ms，六项基础检查正确，首次补全 947.8ms。没有把“初始化结束”当作 semantic READY，也没有将初始化时间混入上述请求分位数。

已实证的两项降级原因：

1. **Windows 盘符身份误判。** 当前 release 侧车通过公开 NDJSON initialize 正常启动并返回 `file:///d:/code/applications_photos`；Node 原生 realpath 为 `<windows-test-path>`。主分支 `src/index/workspace-uri-identity.ts` 的 `isEquivalentWorkspaceIdentity()` 直接比较两个 path.resolve 字符串，结果 false；同一机器 path.relative 结果为空。LSP 日志随后报告索引 degraded、indexedFiles=0，三轮搜索现存 PhotoBrowserActionBar 均返回空数组。
2. **当前工程声明输入不完整。** 初始化的首个阻断项为 AlbumDefine.ts 无法解析 `@ohos.filemanagement.userFileManager`（2307）。API 24 声明清单没有相应文件，工程配置目标为 API 20。没有伪造声明、删除 import 或修改完整性条件来制造 READY；这仍只是首个可见阻断项，后续依赖完整性尚未证明。

以上定位的是两项降级原因；3–4s 查询尚未做 CPU/I/O 分解，不能把全部慢响应都归因于这两项。

第一轮已取回全部 159 个完整响应，并核验工程、81 项运行时/驱动输入、1670 项 SDK 输入前后不变，服务端退出码 0。Photos 的 git archive 为 CRLF、实际工作树为 LF，全部 288 文件经换行归一化恰好匹配；测量绑定的是实际 Windows 工作树字节。后两轮的这些最终标志尚未取回，不作为已复核。

本次保留已有 `<windows-test-path>` 的六项未提交修改。Photos 的原有 `.zed/settings.json` 仍指向旧诊断运行时及 legacy 引用策略；测试直接启动新目录内的服务器，实际编辑器 UI 点击与绘制未自动化。
