# 交互时延评估：500ms体验目标

2026-10-28，依据用户最新明确要求。本文件修订当前时延验收解释，不修改产品代码、运行超时、内存策略或正确性断言。

## 当前口径

- **500ms是性能与体验目标，不是每次操作的严格限制。** 单次或偶发超过目标，不独立判定功能失败，也不单独阻塞交付。
- 按能力和真实场景评估典型体验，同时报告p50/p95/p99/max、超过目标的次数/比例、慢响应的连续性、时间窗口分布和等待来源。
  不只看最快样本、平均数、单个最大值或一个分位数；忙闲、冷启动/热态、首次/重复及缓存命中分开。
- 对可以接受的波动说明当时操作、前置状态、频率、是否自行恢复以及后续交互是否正常。
  对反复或持续的严重慢响应、排队不消退、超时、错误结果、崩溃和功能不可用继续记录并评估影响，不能以“允许波动”掩盖。
- 原始测量、失败样本和计时边界保留；完整响应包含排队、更新、执行、合并及传输。
  超时保留耗时下界/未完成状态，不把失败、取消或部分结果计为快速成功。
- **本次没有新增数值硬线、允许超标比例或持续时长阈值。** 不能自行改成550ms、1s或某个P95/比例作为替代交付硬门槛。
  早期550ms/P95合同及其判定保留为有日期的历史记录，本轮不把它重新套为500ms目标的替代硬线。
- 功能正确性/完整范围、新鲜度、取消/恢复、实际OOM/崩溃/不可用、已有运行截止和资源保护的记录方式不因该调整放宽。
  本次不授予发布/合并，不把尚未完成的UI/平台验证改成通过；Node2048MiB测试豁免仍按其独立授权执行。

功能/协议验证与性能观察分别下结论。一个请求返回正确完整结果但超过目标，可以是功能通过且存在时延观察项；
是否构成交付问题需要结合代表性使用和影响证据说明，不能由`durationMs > 500`直接推出。
也不能因为不再设单次硬门槛，就宣称所有性能问题已解决。

## 历史门禁与自动化边界

`config/semantic-release-matrix.json`、`scripts/bench/assert-semantic-release.mjs`和`prepared-query-report.mjs`
仍保存早期550ms/P95数值判定。此次只更新文档口径，**未改动或运行这些旧门禁以制造PASS**。
其旧数值FAIL不直接等于当前体验口径下功能失败，也不得仅据此把偶发越目标作为本轮交付阻塞；
其他正确性、超时、资源或证据不足的失败仍逐项有效。旧结果不能直接改标为新口径通过。
后续若让这些工具承担当前口径的自动验收，须先明确区分客观统计/功能失败/体验评估，按仓库TDD验证工具行为；
不能修改数字、吞掉失败或删除原始证据来替代体验判断。

本轮30K混合驱动本就只统计>500ms，并未据此提前停测；本次不需要改驱动、重跑性能测试或产品优化。
