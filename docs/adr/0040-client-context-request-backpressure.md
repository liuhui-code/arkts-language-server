# ADR0040：编辑器自动上下文请求的生产端背压

- 日期：2026-11-02。
- 状态：**Proposed；WUI-003 已授权实现，客户端组件/种子/release 验证通过；不是上游接受、安装或真实 UI 通过。**
- 关联：[WUI-003 / #103](https://github.com/liuhui-code/arkts-language-server/issues/103)、
  [0032](0032-completion-item-identity-and-inferred-roots.md)、[0033](0033-client-navigation-ownership-and-ui-input-context.md)、
  [0037](0037-navigation-work-and-input-validation.md)、[0039](0039-validation-directory-observations.md)。
- 客户端来源：Zed `8dd255c3eafb5231056fe4e6f601cedd011f1c93`，与原 Windows1.25.3 证据版本对应。
  源文件逐个 Git blob 校验与已保存的上游 tree 收据相同；其他版本必须另行核对，不推定当前日常程序已修复。

## 证据与责任边界

当前 server main 已有有限优先、mutation fence、取消和相同请求共享。64 个不同位置/方法的请求均有效，
标准协议没有可靠的“人工 F12 / 编辑预测”来源字段；同一优先级串行执行仍会累积。
0039 的路径核验优化在三轮 30K 对照仅改善约 10%，不能据此关闭 WUI-003。

Zed `RelatedExcerptStore::fetch_excerpts` 选择最多 32 个标识符，在构造 futures 向量时已经调用
`Project::edit_prediction_definitions`；后者同时启动 definition 和 typeDefinition。
因此随后把 `join_all` 改为有界消费并不能限制已经启动的 64 个请求。
原现场 32 对位置还与光标47:45的距离顺序、附近三行及当前方法签名全部吻合。
这是强源码对应；原进程没有客户端调用栈/功能开关快照，不将其伪装成原现场唯一触发来源的运行时证明。

生产接口回归原版 **RED：64 个请求在首个响应之前全部发出**；新候选 **GREEN：首轮只发一对**，
人工 Project 定义可插入，最终全部 64 个不同方法/位置仍完成；热命中和上下文销毁对照保留。
该测试是实际客户端组件＋framed 内存测试 LSP，不是真实桌面 UI，也不是语言服务器 child stdio 测试。
服务端正确性仍使用本仓库真实 child stdio 回归；30K 另外对照生产节奏，只称协议实验。

## 成熟机制与选择

采用有界惰性请求生产，而非服务端猜测请求意图。参考
[futures 0.3.34 StreamExt::buffered](https://docs.rs/futures/0.3.34/futures/stream/trait.StreamExt.html#method.buffered)：
限制同时轮询的 Future 并保留结果顺序；**Project Task 必须在被轮询时才创建**。
依赖锁定版本正是0.3.34。Context7解析传输失败，按官方库文档及固定上游源码核对。

自动上下文一次处理一个标识符。每个具备两个能力的语言服务器最多接收这一对请求；
不是全项目只准两个请求，也不是减少32个标识符。完整结果、两种请求、命中、距离排序和原 debounce 保留。
这匹配本服务端串行 compiler 的实际容量；人工请求不归此生产器管理，不被其停止或替代。
其他生产器和其他服务器各自独立，不能把此局部背压宣传为全局请求并发上限。

## 生命周期与不变量

- 尚未轮询的标识符不持有已发出的 LSP 请求；销毁上下文不继续创建余下请求。
- 延迟生产跨越用户编辑/后续 refresh，必须绑定当前源版本和 refresh 身份，在准入、异步返回和最终发布处检查。
  过时上下文不能产生后续预取或把部分旧缓存提交给新上下文；保持实际输入、独立人工请求与原服务端新鲜度合同。
- 仍存活的过时 refresh 必须有明确终态及可辨别的 superseded 信息；不能留下 Started 却没有结束，
  也不能把取消的部分上下文标成完整语义成功。已销毁 owner 不再发布事件。
- 服务端取消、在途不可中断阶段、watchdog/恢复预算和请求单一终态不改变；不新增超时、RSS 或项目成员阈值。
- 0033 保护最终界面导航所有权，本决策控制自动请求的产生速率。两者独立；只装 server/扩展 launcher
  都不会修改 Zed 客户端逻辑。交付独立、固定版本的客户端源码补丁，不替换日常编辑器。
- 已完成客户端缓存的原有跨依赖有效性语义保留；本决策防止过时的延迟工作产生或提交部分结果，
  不以此声称现有缓存拥有更强的跨依赖新鲜度证明。

## 替代方案及限制

不按突发形态推断并丢弃服务器合法请求，不用全路径小写或跨请求 `valid=true` 缓存换速度，
不关闭编辑预测/类型定义、不缩小上下文、不增加 Worker 并发，也不改 LSP 超时。
服务端支持显式 background origin 或批量语义事务是其他协议设计，不能暗中加入标准请求。

单个正在执行的慢后台请求仍可能阻塞人工查询；本决策限制前面自动请求数量，不能保证任意慢请求都在500ms内。
后台完整取齐所有位置仍有总成本，不能把低人工延迟冒充64条的总耗时消失。
这是该Zed上下文生产器的统一策略，不按服务器名字特判；在可高度并行的其他语言服务器或高RTT远程会话上，
它可能延长自动上下文取齐时间。选择一个标识符是针对本轮串行后端容量的保守取舍；
本轮未建立这些其他后端的吞吐结论，广泛部署前须另行衡量，未为此新增设置或协议。
其他客户端、未包含补丁的 Zed、多服务器及 UI 自然输入仍需各自实测；原 Windows/UI 和耐久缺口不追认通过。

## 验证与交付

先通过原组件表征，再保留64→2的公开生产端 RED/GREEN；覆盖人工查询、全部后台答案、缓存、销毁、
源编辑/refresh交错及终态。组件完整测试、种子对照和相关 release build 分开记录。
同30K/SDK/Node/server输入，用不截断的64条原请求＋固定人工目标，对照 eager 与有界生产，记录人工/后台耗时、
错误、Program/Worker及资源；不得在编译/其他压力测试并行时测这组延迟。
报告真实运行范围、补丁部署边界及未覆盖项，不自动发布、合并或提交上游PR，不移除上游人工 review 标记。
